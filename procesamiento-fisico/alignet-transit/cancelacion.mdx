Usa `POST /cancel` para solicitar la cancelación de una autorización iniciada con `POST /authorize` que **todavía continúa en curso**.

<CardGroup cols={2}>
  <Card title="Cancelar autorización activa" icon="ban">
    Usa `POST /cancel` mientras la autorización original sigue en curso. La cancelación identificada se devuelve como `DENIED`, código `14` y mensaje `"Operación cancelada"`.
  </Card>
  <Card title="Extornar venta aprobada" icon="rotate-left" href="/procesamiento-fisico/alignet-transit/extorno">
    Si la venta ya terminó como `APPROVED`, usa `POST /reversals`.
  </Card>
</CardGroup>

| Decisión | Endpoint | Resultado exitoso |
| --- | --- | --- |
| Interrumpir una autorización activa | `POST /cancel` | HTTP `200`, `status: "DENIED"`, `resultCode: "14"` y `resultMessage: "Operación cancelada"`. |
| Revertir una venta aprobada | `POST /reversals` | HTTP `200` con `status: "REVERSED"` y `resultCode: "00"`. |

<Warning>
  No uses `/cancel` para una venta ya aprobada y no uses `/reversals` para cancelar una autorización activa. Son operaciones distintas.
</Warning>

## Comportamiento durante la cancelación

Pay-me verifica la operación mientras procesa `/cancel`:

- Si la autorización sigue en curso, procesa la cancelación.
- Si el cobro se aprobó mientras se procesaba la cancelación, Pay-me ejecuta internamente el extorno correspondiente.

Este extorno interno forma parte del procesamiento de `/cancel`. Es distinto del extorno que solicitas explícitamente mediante `POST /reversals` cuando ya conoces que una venta terminó como `APPROVED`. No envíes una reversa adicional sin verificar primero el estado actualizado.

La solicitud original de `/authorize` puede permanecer abierta hasta completar su tiempo de espera, aunque la cancelación ya se haya procesado y el PINPAD haya salido de la pantalla de pago. Un HTTP `202 PENDING` posterior de `/authorize` indica que venció esa espera: no invalida una cancelación confirmada ni determina por sí solo el estado final.

## Solicitud

`POST /cancel` se consume en el mismo host y puerto configurados para `POST /authorize`.

```http
POST /cancel
Content-Type: application/json
```

URL completa:

```text
http://<IP_DEL_PINPAD>:<PUERTO>/cancel
```

### Cuerpo JSON confirmado

```json
{
  "operationNumber": "44992528"
}
```

| Campo | Tipo | Obligatorio | Descripción |
| --- | --- | --- | --- |
| `operationNumber` | String | Sí | El mismo número de operación enviado en la autorización original que continúa en curso. |

No generes otra referencia y no envíes monto, moneda, medio de pago ni datos de tarjeta.

### cURL

```bash
curl --request POST "http://<IP_DEL_PINPAD>:<PUERTO>/cancel" \
  --header "Content-Type: application/json" \
  --max-time 110 \
  --data '{"operationNumber":"44992528"}'
```

Reemplaza la IP y el puerto por los mismos valores usados para `POST /authorize`.

## Respuestas confirmadas

Cuando el POST responde HTTP `200`, evalúa conjuntamente `status`, `resultCode` y `resultMessage`: un HTTP `200` o un estado `DENIED` aislado no identifican una cancelación. Al finalizar el flujo, consulta `GET /payments/{operationNumber}` para verificar el resultado actualizado.

| HTTP | Resultado o situación | Acción del sistema central |
| --- | --- | --- |
| `200` | `DENIED`, `resultCode: "14"` y `resultMessage: "Operación cancelada"`. | Identifica el resultado de cancelación y verifica el estado actualizado mediante `GET /payments/{operationNumber}`. |
| `200` | Otros resultados `DENIED`. | No los clasifiques automáticamente como cancelación. Conserva el código y mensaje y consulta el estado actualizado. |
| `202` | Venció la espera de 90 segundos. El resultado continúa pendiente e incluye `Retry-After`. | Mantén la operación abierta, espera el intervalo indicado y no asumas éxito ni fallo. |
| `404` | El `operationNumber` no existe en ese PinPAD. | Verifica la referencia y que la solicitud se envió al mismo PinPAD de la autorización original. |
| `503` | El SDK no está listo o no hay una pantalla disponible. | Restablece la disponibilidad del PinPAD antes de volver a intentar. |

<Warning>
  HTTP `202` no es una cancelación exitosa ni fallida. Consulta el estado actualizado; no inicies un extorno ni cierres la operación solo por haber recibido `202`.
</Warning>

## Ejemplos de respuesta

<AccordionGroup>
  <Accordion title="Cancelación identificada — 200 DENIED, código 14" defaultOpen icon="ban">

Los ejemplos de HTTP `200` muestran únicamente los campos de decisión confirmados; conserva cualquier campo adicional que entregue la implementación.

```json
{
  "operationNumber": "44992528",
  "status": "DENIED",
  "resultCode": "14",
  "resultMessage": "Operación cancelada"
}
```

Esta combinación identifica el resultado de cancelación. Verifica el estado actualizado mediante `GET /payments/{operationNumber}` antes de cerrar la operación. No sobrescribas este resultado final con un `PENDING` tardío de `/authorize`.

  </Accordion>

  <Accordion title="Otros resultados DENIED" icon="circle-xmark">

```json
{
  "operationNumber": "44992528",
  "status": "DENIED"
}
```

El estado `DENIED` aislado no permite identificar una cancelación. Revisa el código y el mensaje entregados por Pay-me: la combinación `DENIED`, `14` y `"Operación cancelada"` corresponde a cancelación; otros resultados `DENIED` deben evaluarse según su código y mensaje. Consulta el estado actualizado antes de decidir.

  </Accordion>

  <Accordion title="Resultado pendiente — 202 Accepted" icon="clock">

```http
HTTP/1.1 202 Accepted
Retry-After: <segundos>
```

Respeta el valor de `Retry-After` antes de cualquier acción posterior. La espera interna venció, pero este cuerpo no informa todavía el resultado final.

  </Accordion>

  <Accordion title="Operación inexistente — 404 Not Found" icon="magnifying-glass">

```http
HTTP/1.1 404 Not Found
```

El número de operación no existe en el PinPAD que recibió la solicitud. Verifica tanto la referencia como el terminal de destino.

  </Accordion>

  <Accordion title="PinPAD no disponible — 503 Service Unavailable" icon="terminal">

```http
HTTP/1.1 503 Service Unavailable
```

El SDK no está listo o no existe una pantalla disponible para procesar la solicitud. Recupera la disponibilidad antes de reintentar.

  </Accordion>
</AccordionGroup>

## Verificar el resultado final

1. Conserva el `operationNumber` original y los resultados recibidos en almacenamiento persistente.
2. Consulta `GET /payments/{operationNumber}` al finalizar el flujo, incluso después de HTTP `200`, para verificar el resultado de la autorización o cancelación.
3. Respeta `Retry-After` cuando corresponda. Antes de confirmar, cerrar, reintentar o solicitar otra acción, verifica el estado actualizado. Si sigue pendiente o indeterminado, mantén la operación pendiente.
4. No sobrescribas un resultado final ya confirmado con un `PENDING` tardío de `/authorize`. No asumas un resultado financiero por el vencimiento de la espera ni por la salida de la pantalla de pago.
5. La autorización y el extorno tienen resultados separados. `GET /reversals/{operationNumber}` verifica el extorno solicitado mediante `/reversals`; no lo sustituyas por la consulta de autorización o cancelación.

<Note>
  La consulta del flujo de autorización o cancelación se realiza mediante `GET /payments/{operationNumber}`. No está confirmado en la implementación disponible cómo se registra el extorno interno generado durante `/cancel`, ni si queda expuesto en `GET /reversals/{operationNumber}`. Si el resultado actualizado no permite resolver la operación, mantenla pendiente y coordina su conciliación con Pay-me antes de solicitar otra acción.
</Note>

## Flujo recomendado para el sistema central

<Steps>
  <Step title="Comprueba que la autorización sigue activa">
    Usa `/cancel` solo mientras la autorización original continúa en curso. Si ya fue aprobada, sigue el flujo de extorno.
  </Step>
  <Step title="Reutiliza la referencia original">
    Envía el mismo `operationNumber` de `POST /authorize` al mismo host y puerto del PinPAD.
  </Step>
  <Step title="Procesa la respuesta del POST">
    Ante HTTP `200`, identifica la cancelación con `DENIED`, `14` y `"Operación cancelada"`. No clasifiques otros resultados `DENIED` como cancelación.
  </Step>
  <Step title="Verifica el estado actualizado">
    Consulta `GET /payments/{operationNumber}` antes de confirmar, cerrar, reintentar o solicitar otra acción. Respeta `Retry-After` cuando corresponda. Mantén pendientes los resultados pendientes o indeterminados y conserva cualquier resultado final ya confirmado frente a un `PENDING` tardío.
  </Step>
</Steps>
