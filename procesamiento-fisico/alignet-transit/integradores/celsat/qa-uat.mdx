Las pruebas deben validar el contrato HTTP, la interacción con el P5L, la interpretación de estados y la recuperación ante resultados inciertos. Cada caso debe conservar evidencia correlacionada mediante `operationNumber` y, cuando exista, `transactionID`.

## Preparación

| CELSAT | Alignet | Compartido |
| --- | --- | --- |
| SCC o simulador, referencias, montos, lógica operativa y evidencia. | Componente Local, P5L, PaymePOS SDK, plataforma y evidencia de procesamiento. | Conectividad LAN, ejecución, análisis y aceptación. |

Antes de ejecutar los casos, verifica:

- SCC o simulador disponible;
- P5L asignado y preparado para el ambiente;
- URL base y mecanismo de autenticación confirmados;
- conectividad LAN entre el SCC y el Componente Local;
- timeouts iniciales configurados;
- operaciones abiertas persistidas por el SCC;
- logs correlacionados habilitados;
- versión de la especificación registrada.

## Escenarios de autorización

| Escenario | Resultado esperado | Evidencia mínima |
| --- | --- | --- |
| Pago autorizado | `success = true`, `resultCode = "00"` y `state = "AUTORIZADO"`. | Solicitud, respuesta y ambos identificadores. |
| Pago denegado | `success = true`, `resultCode = "01"` y `state = "DENEGADO"`. | Código, estado y razón. |
| Pago con información adicional | La respuesta conserva `montoPeaje`, `montoDetraccion` e `IdTurnoVia` en `result.additionalFields`. | Solicitud y respuesta correlacionadas. |
| Solicitud inválida | `resultCode = "06"`. | Payload enviado y mensaje de validación. |
| Configuración de comercio inválida | `resultCode = "08"`. | Respuesta y escalamiento técnico. |
| Cancelación antes de presentar tarjeta | `success = false`, `resultCode = "14"` y `result = null`. | Respuesta local. |
| Cancelación después de un intento | `success = false`, `resultCode = "15"` y `result = null`. | Respuesta local. |
| Dispositivo no registrado | `resultCode = "P01"`. | Serial del terminal y respuesta. |
| Dispositivo no inicializado | `resultCode = "P04"`. | Estado del terminal y respuesta. |
| Batería baja | `resultCode = "P05"`. | Respuesta local. |
| Impresora no disponible | `resultCode = "P06"` o `"P07"`. | Respuesta y condición física. |

## Escenarios de recuperación

| Escenario | Resultado esperado |
| --- | --- |
| Timeout durante el `POST` | El SCC conserva `operationNumber` y ejecuta el `GET` antes de cualquier nueva venta. |
| `state = PENDIENTE` | El SCC mantiene la operación abierta y consulta el estado. |
| Pérdida de la LAN | Después de la reconexión, el SCC consulta las operaciones abiertas. |
| Reinicio del SCC | El SCC recupera las referencias persistidas y consulta cada operación pendiente. |
| Respuesta duplicada | El SCC procesa el resultado de forma idempotente. |
| Código desconocido | El SCC conserva el valor original y escala sin asumir su significado. |

## Validaciones de contrato

<Check>
  La solicitud contiene `operationNumber`, `amount` y `currency` como campos requeridos, y admite `additionalFields` como objeto opcional.
</Check>

<Check>
  `amount` y `currency` se envían como cadenas. El contenido de `amount` representa un entero positivo en unidades menores.
</Check>

<Check>
  `montoPeaje` y `montoDetraccion` se envían como cadenas decimales con dos posiciones, e `IdTurnoVia` conserva la capitalización documentada.
</Check>

<Check>
  La respuesta devuelve en `result.additionalFields` la información adicional asociada a la operación.
</Check>

<Check>
  El SCC no interpreta `success = true` como aprobación.
</Check>

<Check>
  El pago solo se confirma cuando `result.state = "AUTORIZADO"`.
</Check>

<Check>
  Un timeout no genera automáticamente un nuevo `operationNumber`.
</Check>

<Check>
  La consulta utiliza `GET /api/v1/payments/{operationNumber}`.
</Check>

<Check>
  La evidencia no contiene datos sensibles de tarjeta.
</Check>

## Criterios de salida

La integración puede avanzar cuando:

- los endpoints responden de acuerdo con el contrato;
- CELSAT interpreta correctamente todos los estados financieros;
- los códigos locales y del procesador producen el tratamiento esperado;
- timeout, reconexión y reinicio no generan cobros duplicados;
- `operationNumber` y `transactionID` permiten correlacionar la evidencia;
- la información adicional se conserva entre la solicitud y la respuesta;
- los parámetros ajustables del ambiente han sido registrados;
- ambas partes aprueban los resultados de integración y UAT.

## Evidencia por caso

Registra:

- identificador del caso;
- fecha y hora;
- ambiente y versión de interfaz;
- SCC y P5L utilizados;
- `operationNumber` y `transactionID`, cuando exista;
- solicitud y respuesta sanitizadas;
- `success`, `resultCode`, `resultMessage`, `state` y `stateReason`;
- tiempos observados;
- resultado esperado y obtenido;
- observaciones y conformidad.
