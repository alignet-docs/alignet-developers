La certificación debe validar el contrato HTTP, la interacción física con el Wiseasy P5L, la decisión de negocio y la recuperación sin doble cobro. Las tablas describen **resultados esperados**, no pruebas ejecutadas. Registra el resultado real y su evidencia antes de marcar un criterio como cumplido.

## Preparación

Antes de ejecutar casos:

- registra la versión de Pay-me PinPAD instalada;
- confirma la asociación entre sistema central, punto de atención y Wiseasy P5L;
- configura una IP estable y el puerto del terminal;
- ejecuta `GET /health` desde el sistema central;
- completa la verificación de llaves en el terminal;
- configura el timeout de autorización en al menos 100 a 110 segundos para las pruebas;
- habilita persistencia y logs sanitizados;
- acuerda referencias, montos y medios de pago de prueba.

## Casos de contrato

| Caso | Estímulo | Resultado esperado |
| --- | --- | --- |
| Disponibilidad | `GET /health` | HTTP `200`, `status: "UP"`, `service: "Alignet ECR"`. |
| Solicitud mínima | `operationNumber`, `amount`, `currency` y `paymentMethod` válidos | La autorización se procesa sin error de validación. |
| Solicitud completa | Incluye campos obligatorios, `tollData` y `additionalFields` con valores String | La autorización se procesa sin error de validación. |
| Referencia numérica | `operationNumber: "44992528"` | Se acepta como String numérico. |
| Referencia con caracteres no numéricos | Incluye letras, guiones, espacios u otros caracteres | HTTP `400` con `BAD_REQUEST`. |
| Monto como cadena | `amount: "100"` | Se acepta como String numérico en unidades menores. |
| Monto como número JSON | `amount: 100` | HTTP `400` con `BAD_REQUEST`. |
| Moneda como cadena | `currency: "604"` | Se acepta como String numérico de tres dígitos. |
| Moneda como número JSON | `currency: 604` | HTTP `400` con `BAD_REQUEST`. |
| Moneda ausente | No incluye `currency` | HTTP `400` con `BAD_REQUEST`. |
| Método de pago | Ejecuta solicitudes independientes con `paymentMethod: "CARD"` y `paymentMethod: "QR"` | Cada valor se acepta por separado. |
| Método de pago ausente | No incluye `paymentMethod` | HTTP `400` con `BAD_REQUEST`. |
| Métodos de pago simultáneos | Envía `CARD` y `QR` juntos, como arreglo o valor combinado | HTTP `400` con `BAD_REQUEST`. |
| Método de pago inválido | Envía un valor distinto de `CARD` o `QR` | HTTP `400` con `BAD_REQUEST`. |
| Referencia inválida | Vacía o no numérica; prueba límites según la tabla de parámetros tras contrastarla con ECR | HTTP `400` con `BAD_REQUEST`. |
| Monto inválido | Cero, negativo, decimal, no numérico o mayor de 12 dígitos | HTTP `400` con `BAD_REQUEST`. |
| Moneda inválida | No contiene exactamente tres dígitos | HTTP `400` con `BAD_REQUEST`. |
| Campo adicional inválido | Valor que no es String | HTTP `400` con `BAD_REQUEST`. |

## Casos transaccionales

| Caso | Resultado esperado | Decisión del sistema central |
| --- | --- | --- |
| Pago aprobado | HTTP `200`, `APPROVED`, `00`, código de autorización y fecha final. | Confirmar y aplicar la regla de apertura. |
| Pago rechazado | HTTP `200`, `DENIED` y código distinto de `00`. | No confirmar. |
| Extorno explícito CARD aprobado | HTTP `200`, `REVERSED` con `00`, `16` o `17`. | Registrar extorno confirmado o éxito equivalente. |
| Extorno pendiente | HTTP `202`; `SEARCHING`, `PROCESSING` o `PENDING`. `P22` se clasifica como `PENDING`. | Esperar `Retry-After: 2` y consultar `GET /reversals/{operationNumber}`. |
| Extorno denegado | HTTP `200`, `DENIED`. | No registrar como extornado ni reintentar automáticamente. |
| Cobro sin confirmar | HTTP `202`, `UNKNOWN`: aún no se sabe si se cobró. | Seguir consultando con la misma referencia, sin otro cobro. |
| Extorno sin confirmar | HTTP `502`, `UNKNOWN`: la solicitud terminó con error. El cuerpo incluye solo `operationNumber`, `status` y `message`. | Revisar si se ejecutó el extorno; no registrar éxito ni reenviar automáticamente. |
| Código SDK vacío | El SDK no entrega `resultCode`. | La app utiliza el nombre del estado; no inventar otro código. |
| Método incorrecto | Usar un método no admitido en una ruta válida. | HTTP `405`, `METHOD_NOT_ALLOWED`. |
| Consulta inválida | Consultar `/payments` o `/reversals` con segmento vacío o inválido. | HTTP `400`, `ERROR`, `BAD_REQUEST`. |
| Headers de respuesta | Todas incluyen `Cache-Control: no-store`; HTTP `202` añade `Retry-After: 2`. | Comprobar headers y respetar el intervalo de consulta. |
| Espera agotada | HTTP `202`, `PENDING`, `WAITING_RESULT`. | Consultar, sin nuevo cobro. |
| Terminal ocupado | Otra referencia durante un cobro activo devuelve `409 POS_BUSY`. | Esperar y reintentar cuando se libere. |
| Terminal no listo | HTTP `503 POS_NOT_AVAILABLE`. | Recuperar disponibilidad antes de reintentar. |
| Referencia inexistente | La consulta devuelve `404 NOT_FOUND`. | Verificar la referencia; no asumir rechazo financiero. |

## Validación de cancelación

Aplica estos casos a CARD y QR. El servicio valida ejecución y correspondencia con la operación; el cierre visual no acredita éxito.

| Caso | Estímulo | Resultado esperado |
| --- | --- | --- |
| Cancelación rechazada con `14` | Recibir `DENIED/14`, incluso con mensaje `Operación cancelada`. | No reconocer cancelación exitosa; consultar el cobro original. |
| Cancelación confirmada | Cancelar una autorización activa y obtener un resultado de esa operación. | `CANCELLED` con `00`, `16` o `17`, validado por el servicio; reconocer el resultado sin consulta obligatoria. |
| Éxito equivalente de cancelación | Recibir HTTP `200`, `CANCELLED` con `16` o `17`. | Reconocer cancelación validada; conservar el código SDK sin convertirlo a `00`. |
| Cancelación no ejecutada | Simular un fallo que impida ejecutar la cancelación. | Respuesta de error, sin informar éxito; consultar el cobro original. No se anticipan HTTP, código ni mensaje del nuevo error. |
| Resultado de otra operación | Entregar al servicio un resultado que no corresponda al `operationNumber` solicitado. | Rechazarlo con una respuesta de error; no cerrar la operación como cancelada. |
| Cancelación denegada | Obtener `DENIED` con `14`, `15`, `18`, `19`, `20`, `01`, `03` u otro código SDK. | Cancelación rechazada o abandonada; recuperar el cobro original sin asumir su resultado. |
| Segunda cancelación concurrente | Enviar otro `/cancel` para la misma referencia mientras se procesa el primero. | HTTP `409`, `ERROR`, `CANCELLATION_IN_PROGRESS`; no repetir el POST. |
| Venta no encontrada | Obtener `05` o `07` del SDK en cancelación. | HTTP `404`; no inferir el resultado financiero del cobro. Verificar el código del cuerpo conforme al [pendiente técnico](/procesamiento-fisico/alignet-transit/datos-por-validar#contrato-y-habilitaci%C3%B3n). |
| Timeout o incertidumbre | Perder la respuesta o recibir HTTP `202`, `PENDING` con `P22` o `WAITING_RESULT`. | Mostrar **Cancelación no confirmada**; consultar el cobro original, respetando `Retry-After: 2` en HTTP `202`. |

Comprueba que `GET /payments/{operationNumber}` informa el cobro original, no el resultado de la solicitud de cancelación. Si devuelve `PROCESSING`, `PENDING` o `UNKNOWN`, conserva la referencia y no habilites otro cobro. Los ciclos repiten solo el GET.

## Cancelación CARD

| Caso | Estímulo | Resultado esperado |
| --- | --- | --- |
| Cobro aprobado tras cancelación fallida | Recuperar `APPROVED/00` en el cobro original. | Evaluar un extorno independiente con `POST /reversals` y el `operationNumber` de la venta, sin duplicados. Reconocer éxito con `REVERSED` y `00`, `16` o `17`; consultar `/reversals/{operationNumber}` si no está confirmado. |

No debe generarse un extorno automático ante cualquier error de cancelación. Presenta la tarjeta cuando el PinPAD la solicite en el extorno.

## Cancelación QR

| Caso | Estímulo | Resultado esperado |
| --- | --- | --- |
| QR pendiente | Generar el QR sin pagar. | Ya existe la transacción pendiente asociada al `operationNumber`; mostrar o escanear no confirma el pago. |
| Cancelación validada | Cancelar o inhabilitar el QR pendiente. | Reconocer `CANCELLED` con `00`, `16` o `17`, sujeto a la validación del servicio. |
| Pago aprobado tras cancelación fallida | Recuperar `APPROVED/00` en el cobro original. | Conservar el pago aprobado y registrar la discrepancia. Ni `/cancel` ni refund devuelven el monto; no enviar `/reversals`. |

## Casos de idempotencia y recuperación

| Caso | Validación esperada |
| --- | --- |
| Misma referencia durante el proceso | El segundo envío no inicia otro cobro y devuelve `202` con el estado actual. |
| Misma referencia finalizada | Devuelve `200` con el resultado guardado sin otro cargo. |
| Otra referencia concurrente | Devuelve `409 POS_BUSY`. |
| Timeout del sistema central | El sistema central consulta la referencia original antes de aceptar otro intento. |
| Pérdida de red | Al reconectar, el sistema central consulta las operaciones abiertas. |
| Reinicio del sistema central | Recupera las referencias guardadas y consulta los cobros cuyo resultado aún no conoce. |
| Reinicio del P5L durante el cobro | `UNKNOWN` devuelve HTTP `202`: sigue consultando; no marques el cobro como aprobado ni rechazado. |
| `202` repetido | El sistema central respeta `Retry-After` y aplica el límite de consulta acordado. |

## Criterio de aceptación

No habilites producción mientras exista riesgo de interpretar `PENDING`, `UNKNOWN`, timeout o `404` como rechazo y generar un cobro adicional. La salida requiere demostrar que toda operación incierta conserva su referencia original hasta resolverse o escalarse.
