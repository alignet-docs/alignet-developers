Usa `POST /reversals` para solicitar el **extorno total de una venta que ya fue aprobada** mediante `POST /authorize`.

<CardGroup cols={2}>
  <Card title="Cancelar autorización activa" icon="ban" href="/procesamiento-fisico/alignet-transit/cancelacion">
    Usa `POST /cancel` mientras la autorización original continúa en curso.
  </Card>
  <Card title="Extornar venta aprobada" icon="rotate-left">
    Usa `POST /reversals` cuando la venta original ya terminó como `APPROVED`.
  </Card>
</CardGroup>

En ambos flujos se reutiliza exactamente el `operationNumber` enviado en la autorización original, pero los endpoints y sus resultados son distintos.

<ParamField path="POST /reversals" type="endpoint" />

<Info>
  Este endpoint pertenece a la interfaz local entre el sistema central y Pay-me PinPAD. No corresponde a `DELETE /charges` de la API de e-commerce.
</Info>

## Cancelación y extorno no son sinónimos

| Aspecto | Cancelación | Extorno |
| --- | --- | --- |
| Estado de la autorización original | Continúa en curso. | Ya finalizó como `APPROVED`. |
| Acción | Intenta interrumpir la autorización activa. | Revierte una venta aprobada. |
| Endpoint | `POST /cancel`. | `POST /reversals`. |
| Resultado exitoso | `CANCELLED`. | `REVERSED` junto con `resultCode: "00"`. |
| Más información | [Cancelación de una autorización en curso](/procesamiento-fisico/alignet-transit/cancelacion). | Esta página. |

## Solicitud

```http
POST /reversals
Content-Type: application/json
```

URL completa:

```text
http://<IP_DEL_PINPAD>:<PUERTO>/reversals
```

### Cuerpo JSON

```json
{
  "operationNumber": "44992528"
}
```

| Campo | Tipo | Obligatorio | Validación | Descripción |
| --- | --- | --- | --- | --- |
| `operationNumber` | String | Sí | Cadena numérica de 1 a 64 dígitos. | Referencia original de `POST /authorize`. Identifica la venta aprobada que se extornará. |

No incluyas `amount`, `currency`, medio de pago ni datos de tarjeta. El extorno es total.

### cURL

```bash
curl --request POST "http://<IP_DEL_PINPAD>:<PUERTO>/reversals" \
  --header "Content-Type: application/json" \
  --max-time 110 \
  --data '{"operationNumber":"44992528"}'
```

Reemplaza la dirección y el puerto por los configurados en tu Wiseasy P5L. Usa exactamente el mismo `operationNumber` de la autorización aprobada.

## Respuestas de `POST /reversals`

Cuando el POST responde HTTP `200`, el cuerpo de **esa misma respuesta** contiene el resultado final. No ejecutes un GET como paso obligatorio del flujo exitoso. Evalúa primero el código HTTP y después `status` y `resultCode`.

| HTTP | Resultado | Significado | Acción del sistema central |
| --- | --- | --- | --- |
| `200` | `REVERSED` + `00` | Se extornó una venta aprobada. Puede ser el resultado recién obtenido o uno previamente guardado. | Registra el extorno y conserva el código de autorización. |
| `200` | `DENIED` | El procesador rechazó el extorno. | No lo registres como extornado ni reintentes automáticamente. |
| `202` | `PENDING` | Venció la espera y el extorno continúa pendiente. | Respeta `Retry-After` y recupera el resultado antes de decidir. |
| `400` | `BAD_REQUEST` | La solicitud es inválida. | Corrige el body antes de reenviar. |
| `404` | `NOT_FOUND` | No se encontró la venta original. | Verifica `operationNumber` y el terminal consultado. |
| `409` | `POS_BUSY` | Otra referencia ocupa el terminal. | Espera a que el terminal se libere. |
| `502` | `UNKNOWN` | No se pudo determinar el estado de la venta. | No reintentes en bucle; escala a Alignet. |
| `503` | `POS_NOT_AVAILABLE` | El SDK de pagos no está disponible. | Restablece el terminal y reintenta cuando esté listo. |

## Recuperar un resultado incierto

El GET no forma parte del flujo normal después de HTTP `200`. Úsalo únicamente después de HTTP `202`, un timeout o una pérdida de conexión:

```http
GET /reversals/{operationNumber}
```

```bash
curl -i "http://<IP_DEL_PINPAD>:<PUERTO>/reversals/44992528"
```

| Código HTTP | Significado | Acción del sistema central |
| --- | --- | --- |
| `200 OK` | La solicitud tiene un resultado final como `REVERSED` o `DENIED`. | Evalúa `status` y `resultCode`. |
| `202 Accepted` | La reversa continúa en curso. | Respeta `Retry-After` y vuelve a consultar. |
| `404 Not Found` | No existe una solicitud registrada con esa referencia. | Verifica la referencia y el terminal. No asumas un resultado financiero. |
| `502 Bad Gateway` | La operación quedó en `UNKNOWN` según la guía técnica. | No reintentes en bucle; escala con la evidencia disponible. |

`GET /payments/{operationNumber}` consulta la **autorización original**. `GET /reversals/{operationNumber}` consulta el **extorno**. Usa ambas vistas para conciliar una operación incierta.

## Estados y códigos de resultado

| `status` | Final | Significado | Acción |
| --- | --- | --- | --- |
| `RECEIVED` | No | Solicitud recibida y validada. | Espera o consulta. |
| `SEARCHING` | No | Pay-me PinPAD busca la venta original. | Espera o consulta. |
| `PROCESSING` | No | La reversa está en ejecución. | Consulta; no reenvíes en paralelo. |
| `PENDING` | No | Venció la espera HTTP, pero el extorno puede continuar. | Consulta y respeta `Retry-After`. |
| `REVERSED` | Sí | Extorno aprobado. | Confirma solo junto con `resultCode: "00"`. |
| `DENIED` | Sí | Extorno rechazado por el procesador. | No confirmes ni reintentes automáticamente. |
| `UNKNOWN` | Requiere revisión | Se perdió certeza sobre el flujo. | Aplica la regla específica y escala. |
| `ERROR` | Depende de la causa | Error de validación u operación. | Trata el código HTTP y `resultCode`. |

| `resultCode` | Contexto | Significado |
| --- | --- | --- |
| `00` | Financiero | Extorno aprobado cuando `status` es `REVERSED`. |
| `01` | Financiero, ejemplo de la guía | Extorno denegado. El catálogo completo está pendiente. |
| `WAITING_RESULT` | Operativo | El extorno sigue pendiente. |
| `BAD_REQUEST` | Validación | Solicitud inválida. |
| `NOT_FOUND` | Búsqueda | No se encontró la venta original. |
| `POS_BUSY` | Concurrencia | El terminal atiende otra operación. |
| `POS_NOT_AVAILABLE` | Disponibilidad | El SDK de pagos no está listo. |

Trata únicamente `REVERSED` junto con `"00"` como extorno aprobado. Conserva cualquier código desconocido y escálalo sin asignarle un significado.

### Tratamiento de `UNKNOWN`

La guía técnica confirma que un `502 UNKNOWN` originado durante la búsqueda de la venta significa que Pay-me PinPAD **no ejecutó** la reversa. Un reinicio durante un extorno puede dejarlo en `UNKNOWN`, pero no está definido si el procesador llegó a recibir la reversa ni un mecanismo automático de conciliación.

<Warning>
  No generalices `UNKNOWN` como “extornado” ni como “no extornado”. Conserva el `operationNumber`, no repitas en bucle y solicita validación a Alignet.
</Warning>

## Timeouts, idempotencia y concurrencia

La espera interna de referencia es de **90 segundos**. Configura `POST /reversals` con al menos **100 a 110 segundos**. Ante `202`, respeta `Retry-After`; si no está presente, la guía propone aproximadamente 2 segundos como referencia inicial.

<Warning>
  El timeout del sistema central describe la conexión, no el resultado del extorno. Consulta `GET /reversals/{operationNumber}` antes de reenviar o tomar una decisión financiera.
</Warning>

El timeout definitivo, el backoff y el tiempo máximo de consulta deben acordarse antes de producción.

`operationNumber` es la clave de idempotencia:

- si el mismo extorno está en proceso, devuelve HTTP `202` y no inicia otro flujo;
- si ya finalizó, devuelve el resultado almacenado y no repite la acción;
- si otra referencia ocupa el terminal, devuelve HTTP `409` con `POS_BUSY`;
- la venta y el extorno se almacenan por separado aunque compartan la referencia.

Usa una sola cola por terminal. Ante una respuesta perdida, consulta primero. Si tu política permite reenviar el POST, conserva exactamente el mismo body y `operationNumber`.

## Flujo recomendado para el sistema central

<Steps>
  <Step title="Confirma que la venta fue aprobada">
    Extorna únicamente una venta con resultado final `APPROVED`. Para una autorización todavía activa, usa `POST /cancel`.
  </Step>
  <Step title="Conserva la referencia original">
    Recupera el mismo `operationNumber` utilizado en `POST /authorize`.
  </Step>
  <Step title="Solicita y procesa el extorno">
    Envía `POST /reversals`. Ante HTTP `200`, confirma solo `REVERSED` junto con `00`; `DENIED` no es un extorno aprobado.
  </Step>
  <Step title="Recupera solo un resultado incierto">
    Ante HTTP `202`, timeout o pérdida de conexión, consulta `GET /reversals/{operationNumber}` y respeta `Retry-After`.
  </Step>
  <Step title="Escala estados indeterminados">
    Ante `UNKNOWN` o un límite de consulta agotado, evita reintentos en bucle y coordina la conciliación con Alignet.
  </Step>
</Steps>

## Garantías y limitaciones

- `REVERSED` junto con `resultCode: "00"` confirma que el procesador aprobó el extorno.
- Un extorno aprobado revierte una venta existente; no equivale a haber impedido la autorización original.
- No está confirmado cuándo se reflejará la reversa para el tarjetahabiente ni su efecto contable después del cierre o liquidación.
- No está confirmada la ventana máxima para extornar, el tratamiento de ventas liquidadas ni la respuesta ante una venta ya extornada.
- El catálogo completo de códigos del procesador y los códigos que permiten reintento están pendientes de confirmación.
- El timeout definitivo de Pay-me PinPAD y el límite de consultas deben validarse en el ambiente objetivo.
