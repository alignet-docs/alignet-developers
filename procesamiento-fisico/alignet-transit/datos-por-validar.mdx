Esta página reúne la información ambigua, incompleta o dependiente de cada implementación. Los valores de referencia sirven para desarrollo y pruebas; no los conviertas en reglas de producción hasta recibir confirmación.

<Warning>
  Estos pendientes no cambian los endpoints ni los contratos documentados. Si una definición futura modifica rutas, campos, tipos o semántica, trata el cambio como una nueva versión de integración.
</Warning>

## Parámetros operativos

| Punto | Referencia disponible | Validación requerida |
| --- | --- | --- |
| Espera interna de Pay-me PinPAD | `90` segundos en desarrollo. | Valor definitivo por ambiente. |
| Timeout del cliente HTTP | Al menos `100–110` segundos con la espera de referencia. | Valor definitivo, siempre superior a la espera del terminal. |
| Frecuencia de consulta | HTTP `202` incluye `Retry-After: 2`. | Backoff y tiempo máximo de consulta por ambiente. |
| Operación no resuelta | No iniciar otro cobro ante `PENDING`, `PROCESSING` o `UNKNOWN`. | Procedimiento de inmovilización, escalamiento y decisión de negocio. |
| Reinicio durante un extorno | Puede producir `UNKNOWN`. | Confirmar si el procesador recibió la reversa y cómo conciliarla. |
| Cancelación con resultado incierto | `POST /cancel` puede responder `202` con `Retry-After`, o perderse la conexión antes de recibir el resultado. | Consultar el cobro original con `GET /payments/{operationNumber}`; no existe consulta de cancelación. Acordar revisión si el cobro continúa sin resolver. |

## Contrato y habilitación

| Punto | Referencia disponible | Validación requerida |
| --- | --- | --- |
| `operationNumber` | La página de parámetros declara `6–12` dígitos; referencias previas declaraban `1–64`. | Contrastar la longitud con ECR vigente. Mantener la tabla de parámetros sin alterar restricciones hasta confirmar. |
| Referencia reutilizada con otro body | No está documentado. | Comportamiento de Pay-me PinPAD; hasta entonces, reenvía exactamente el mismo payload. |
| `additionalFields` | Objeto opcional; todos sus valores son String. | El comercio define las claves que necesita enviar como información complementaria. |
| Monedas | PEN usa `currency: "604"`. | Otras monedas habilitadas para el comercio y el ambiente. |
| Métodos de pago | El contrato admite `CARD` y `QR`, uno por solicitud. | Métodos efectivamente habilitados para el comercio y el ambiente. |
| Códigos financieros | `APPROVED/00` es aprobación; `01` es ejemplo de rechazo. | Catálogo completo por operación y método; `00` aislado no confirma un cobro. |
| Cancelación validada | `CANCELLED` con `00`, `16` o `17`; `DENIED/14` no confirma éxito. | Verificar que la versión instalada aplique el [mapeo vigente](/procesamiento-fisico/alignet-transit/respuesta-estados-y-codigos#c%C3%B3digos-confirmados). |
| Validación fallida de `/cancel` | Si no se ejecutó o el resultado pertenece a otra operación, devolver error, sin informar éxito. | La matriz recibida no especifica HTTP, código ni cuerpo de este error de validación; desarrollo debe definirlos. |
| SDK `05` o `07` en cancelación/extorno | Se clasifican como HTTP `404`. La matriz de cancelación indica `NOT_FOUND`, pero la regla general conserva códigos SDK. | Confirmar qué `resultCode` entrega el cuerpo; no normalizarlo en el cliente. |
| Recepción y corte visual | El PinPAD corta el flujo visual cuando recibe y procesa la solicitud. | Validar fallos de conexión sin presumir recepción o cierre; distinguirlos de fallos internos tras la recepción. |
| Cancelación QR | Solo inhabilita el código; no devuelve pagos. | Evidencia de cancelación ejecutada y correspondencia con la referencia solicitada. |
| `tollData` | Datos estructurados del peaje, con campos String definidos en parámetros. | Confirmar aceptación y restricciones adicionales; no trasladar sus campos a `additionalFields`. |

## Extornos

| Punto | Referencia disponible | Validación requerida |
| --- | --- | --- |
| Extorno tras cancelación fallida | Si el cobro CARD está `APPROVED`, se evalúa `POST /reversals` como acción independiente. | Evidencia del extorno y conciliación cuando no se confirma éxito. |
| Discrepancia de cancelación QR | Solo se cancela o inhabilita el código. Ni `/cancel` ni refund devuelven pagos QR; `APPROVED/00` se conserva como aprobado. | Definir evidencias, responsables y revisión de discrepancias; no generar refund ni reversa. |
| Presentación de tarjeta | El extorno explícito puede requerir interacción con el PinPAD. | Obligatoriedad por versión, uso de tarjeta original y pasos reales. |
| Prevención de duplicados | No extornar si hay un extorno completado o en curso. | Evidencia y consulta para descartar ambos antes de una reversa adicional. |

Confirma también:

- la ventana máxima para solicitar un extorno;
- el tratamiento de ventas cerradas o liquidadas;
- la respuesta de una venta que ya fue extornada;
- cuándo se refleja la reversa para el tarjetahabiente y cuál es su efecto contable;
- la semántica y el procedimiento de conciliación de `UNKNOWN` después de un reinicio;
- los códigos del procesador que permiten reintentar una reversa.

## Infraestructura y soporte

Completa por ambiente:

- la IP, el puerto y la asociación entre sistema central y Wiseasy P5L;
- la versión aprobada de Pay-me PinPAD;
- los contactos, horarios, severidades y procedimiento de soporte;
- los responsables de decidir qué hacer cuando el resultado aún no está confirmado;
- cualquier requisito adicional de seguridad de red.

## Registro de decisión

Por cada punto, registra responsable, definición aprobada, ambiente, fecha de vigencia y evidencia. Conserva este registro junto con la versión de Pay-me PinPAD certificada.
